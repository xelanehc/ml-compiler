The ml-compiler guide

This guide explains the whole project from the beginning: what it does, every concept it uses, how each part is implemented, and why each design choice was made. It assumes you can read C++ and Python and know what a matrix is. It does not assume you know anything about compilers, about how GPT-2 works inside, or about CPU performance.

It is long on purpose. Read it in order the first time; every chapter uses words the earlier ones define. After that, use it as a reference next to the source.

1. The big picture

1.1 What the project is

mlc is a compiler. Its input is a neural network, GPT-2 small, as PyTorch defines it. Its output is a native shared library (a .so file of machine code) with one job: given token ids, compute the same logits PyTorch would, on a CPU, as fast as it can.

The project then measures that library against three existing ways of running the same model: PyTorch itself, torch.compile, and ONNX Runtime.

It exists to learn two things by doing them: how compilers for machine learning work, and how to make numerical code fast. That goal explains several choices that would be wrong in a product. Everything is written from scratch: no LLVM, no BLAS library, no JSON library. Where there was an easy route and an instructive one, the instructive one was taken.

1.2 What "compiling a neural network" means

A trained neural network is two things:

  1. A fixed computation. For GPT-2: look up embeddings, then twelve identical blocks of layer norm, attention, and a small feed-forward network, then one last matrix product. Nothing about which operations run depends on the input. There are no if statements on data.
  2. Numbers. 124 million floating-point parameters (weights) that the computation uses.

PyTorch runs this by interpreting it. Python code calls torch.matmul, which is a C++ function that inspects its arguments, picks an implementation, allocates memory for the result, computes, and returns to Python. Then the next line runs. Each operation is fast inside, but nothing looks across operations, and every call pays for the inspection and allocation.

A compiler does the looking-across ahead of time. Because the computation is fixed, it can be studied once, before any input arrives:

  • Parts that do not depend on the input can be computed once and stored.
  • Sequences of operations can be recognized and replaced by something cheaper.
  • All memory can be laid out in advance, so nothing is allocated while running.
  • The loops for each operation can be generated for the exact sizes involved, with no checks left in them.

The result is a program that does nothing but arithmetic.

This is called ahead-of-time (AOT) compilation: the compiler runs first and produces a file; later, a separate program loads that file and runs it. The opposite is just-in-time (JIT) compilation, where the compiler runs inside the program the first time a piece of code is needed. torch.compile is a JIT.

1.3 Why there are several stages

A compiler is almost always built as a chain of small translations rather than one big one. Each stage has its own way of writing down the program, called an intermediate representation (IR). An IR is just a data structure, chosen so that a particular kind of reasoning is easy.

This project has two IRs because two different kinds of question need answering:

  • "Is this multiplication by 1 pointless? Are these nine operations really a GELU?" These are questions about what is computed. They are easy when the program is a graph of whole-tensor operations and hard when it is a million lines of loops.
  • "Should this loop be split in blocks of 20? Can these iterations run on different threads?" These are questions about how it is computed. They cannot even be asked of a graph, which has no loops.

So the program is first held as a graph IR (operations on whole tensors) and then lowered to a loop IR (loops reading and writing memory). "Lowering" is the standard word for translating from a more abstract form to a more concrete one.

1.4 The pipeline

 PyTorch model (Python)
        │   torch.export + decomposition          [Python, export/]
        ▼
 graph.json + weights.bin                          files on disk
        │   importer                               [src/frontend/]
        ▼
 Graph IR  ── passes: simplify, fold, cse,         [src/graph/]
        │            gelu, attention, layout
        │   lowering + memory planning + staging   [src/loop/lower.cpp]
        ▼
 Loop IR   ── schedule: tile, vectorize,           [src/loop/schedule.cpp]
        │               parallelize                [src/tune/ picks parameters]
        │   code generation                        [src/codegen/]
        ▼
 model.cpp (C++ with NEON intrinsics)
        │   clang++ -O3, linked with the runtime   [runtime/]
        ▼
 model.so  ──  mlc_open(weights) ; mlc_run(inputs, outputs)

One sentence per stage. Each has its own chapter.

  • Export (chapter 3). A Python script asks PyTorch to trace the model into a list of primitive operations and writes that list as JSON, with the weights in a separate binary file. This is the only place PyTorch's own machinery is used to understand the model.
  • Import (chapter 4). The C++ compiler reads the JSON and builds its graph IR: 1062 nodes, each producing one tensor of known type and shape.
  • Graph passes (chapter 6). Six rewrites shrink the graph to 615 nodes and then rearrange the matrix products.
  • Lowering (chapter 7). Every graph node becomes a nest of loops (a kernel). At the same time the compiler decides where in memory every tensor will live, and which values can be computed once at load time.
  • Scheduling (chapters 9, 10, 11). The loops are rewritten to run fast: reordered, split into blocks, marked for SIMD and for threads.
  • Code generation (chapter 8). The loops are printed as C++ text.
  • Build and run (chapter 8). clang++ turns the C++ into machine code. A small handwritten runtime, linked into the same library, maps the weights file into memory and calls the kernels in order.

1.5 Two ideas that run through everything

Static shapes. The compiler is told the sequence length T up front and produces a library for exactly that T. Every tensor's shape is therefore a compile-time constant. This is what makes most of the optimizations possible: you cannot plan memory, or fold the attention mask into a constant, or generate a loop "from 0 to 768" if you do not know the sizes. The cost is one compile per T.

Correctness by comparison (chapter 5). How do you know a compiler is right? Here, by a chain of comparisons. PyTorch's output on a fixed input is saved once (the golden output). A deliberately slow and simple interpreter of the graph IR is checked against it. From then on, everything else is checked against whatever came before it in the chain. The standard is: no logit differs from PyTorch's by more than 0.001, and the most likely next token is the same at every position.

  • The compiler made its own output 12 to 14 times faster on one thread between the first working version and the last.
  • ONNX Runtime is the fair comparison: a mature inference engine whose kernels run on the same CPU instructions ours do. The final build matches it at T=1024 and is behind at smaller sizes, by a few percent on one thread and up to 57% on four.
  • PyTorch is much faster on this machine for a reason outside the project's reach: its matrix products go through Apple's Accelerate library, which uses hardware that ordinary CPU instructions cannot.

2. GPT-2, the program being compiled

A compiler writer has to know the source program well. This chapter is everything GPT-2 small computes in one forward pass, in enough detail that every node in the compiler's graph will be recognizable.

2.1 Tensors

A tensor is an array of numbers with a shape, a list of sizes, one per axis.

  • A scalar has shape [] (no axes, one number). Its rank (number of axes) is 0.
  • A vector of 768 numbers has shape [768], rank 1.
  • A matrix with 16 rows and 768 columns has shape [16, 768], rank 2.
  • GPT-2's attention scores for 12 heads over 16 tokens have shape [12, 16, 16], rank 3.

Every tensor also has a dtype, the type of its elements. This project uses three: f32 (32-bit float), i64 (64-bit integer), and bool.

Throughout, T is the sequence length and the batch size is 1, which is why many shapes start with a 1.

How a tensor is laid out in memory

A tensor's elements are stored in one flat run of memory in row-major order: the last axis varies fastest. For shape [2, 3] the order is

[0,0] [0,1] [0,2] [1,0] [1,1] [1,2]

In general, element [i0, i1, ..., in] of a tensor with shape [n0, n1, ..., nn] is at position

((i0 * n1 + i1) * n2 + i2) ... * nn + in

Equivalently, each axis has a stride, the number of elements you skip when that axis's index goes up by one. The last axis has stride 1; each earlier axis has the stride of the next axis times that axis's size. For shape [12, 16, 64] the strides are [1024, 64, 1].

This matters constantly in later chapters. Walking along the last axis touches consecutive memory. Walking along an earlier axis jumps.

Broadcasting

When an operation combines two tensors of different shapes, PyTorch broadcasts: it lines the shapes up at the right, and wherever one has size 1 (or no axis at all), it behaves as if that tensor were repeated along that axis.

[1, 16, 768]  +  [768]          ->  [1, 16, 768]     the vector is added to every row
[1, 12, 16, 16]  +  [1, 1, 16, 16]  ->  [1, 12, 16, 16]  the same mask for all 12 heads
[1, 12, 16, 64]  *  []          ->  [1, 12, 16, 64]  multiply everything by one scalar

Sizes must be equal or one of them must be 1; anything else is an error.

2.3 The forward pass

Input: ids, shape [1, T], integers in 0..50256. Output: logits, shape [1, T, 50257]. Row t holds a score for every possible next token after position t.

Step 1: embeddings

x = wte[ids] + wpe[0..T-1]            shape [1, T, 768]

wte[ids] is a table lookup: for each token id, take that row of wte. Likewise wpe[t] is the row for position t. Looking up rows by index is called gather in this project (PyTorch calls it embedding or indexing).

Step 2: twelve blocks

Each block does this, with its own weights:

x = x + attention(layer_norm_1(x))
x = x + mlp(layer_norm_2(x))

The x + ... is a residual connection: each sub-block computes a correction that is added to its input.

Layer norm

For each position separately, take its 768-vector v and

mean = (v[0] + ... + v[767]) / 768
var  = ((v[0]-mean)^2 + ... + (v[767]-mean)^2) / 768
out[i] = (v[i] - mean) / sqrt(var + 1e-5) * weight[i] + bias[i]

It rescales each vector to mean 0 and variance 1, then applies a learned per-component scale and shift. 1e-5 (called eps) keeps the division safe when the variance is tiny. Note the variance divides by 768, not 767.

Attention

Attention lets each position gather information from earlier positions.

  1. One linear layer produces three things.

    qkv = h @ c_attn + bias                 [T, 768] @ [768, 2304] -> [T, 2304]
q, k, v = split qkv into three [T, 768] pieces

    @ is matrix multiplication. q, k, v stand for query, key, value.

  2. Split into heads. Each [T, 768] is viewed as [T, 12, 64] and rearranged to [12, T, 64]: 12 heads, each with a 64-vector per position. The rearrangement of axes is a permute (also called transpose).

  3. Scores. For each head, how much should position i attend to position j?

    scores[h, i, j] = (q[h, i, :] . k[h, j, :]) / sqrt(64)       [12, T, T]

    The dot product of i's query with j's key. As a matrix product: q @ transpose(k), with q of shape [12, T, 64] and transpose(k) of shape [12, 64, T]. In the exported graph the division by 8 is done as two multiplications by 64^(-1/4) = 0.3536, one on q and one on k, before the product.

  4. Causal mask. A position may only look at itself and earlier positions (the model predicts the next token, so it must not see it). Scores with j > i are replaced by negative infinity.

  5. Softmax along j turns each row of scores into weights that are positive and sum to 1:

    probs[h, i, j] = exp(scores[h, i, j]) / sum over j' of exp(scores[h, i, j'])

    exp(-infinity) = 0, so masked positions get weight exactly 0.

  6. Mix the values.

    mixed[h, i, :] = sum over j of probs[h, i, j] * v[h, j, :]       [12, T, 64]

    As a matrix product: probs @ v, [12, T, T] @ [12, T, 64].

  7. Merge heads and project. [12, T, 64] is permuted back to [T, 12, 64], viewed as [T, 768], and passed through a second linear layer:

    out = merged @ c_proj + bias              [T, 768] @ [768, 768] -> [T, 768]

MLP

h1  = h @ c_fc + bias                         [T, 768]  @ [768, 3072] -> [T, 3072]
h2  = gelu(h1)
out = h2 @ c_proj + bias                      [T, 3072] @ [3072, 768] -> [T, 768]

GELU is the nonlinearity. GPT-2 uses a specific approximation:

gelu(x) = 0.5 * x * (1 + tanh( sqrt(2/pi) * (x + 0.044715 * x^3) ))

with sqrt(2/pi) = 0.7978845608. It behaves like "keep positive values, squash negative ones towards 0", but smoothly.

Step 3: output

x = layer_norm_f(x)
logits = x @ transpose(wte)                    [T, 768] @ [768, 50257] -> [T, 50257]

The output projection reuses the token embedding table, transposed. This is called weight tying: the same 38.6 million numbers serve as "token to vector" at the start and "vector to token scores" at the end. It shows up several times later, because PyTorch's export materializes that transposed copy (154 MB) on every call, and getting rid of it took until milestone M4.

2.4 Where the arithmetic is

Count multiply-add pairs. A matrix product of an [m, k] matrix with a [k, n] matrix does m * k * n multiplications and as many additions, 2 m k n floating-point operations (flops).

Per layer at sequence length T:

Product Shape flops
c_attn [T,768] @ [768,2304] 2 * T * 768 * 2304
scores [12,T,64] @ [12,64,T] 2 * 12 * T * T * 64
mix [12,T,T] @ [12,T,64] 2 * 12 * T * T * 64
attention c_proj [T,768] @ [768,768] 2 * T * 768 * 768
c_fc [T,768] @ [768,3072] 2 * T * 768 * 3072
MLP c_proj [T,3072] @ [3072,768] 2 * T * 3072 * 768

Plus the output projection once: 2 * T * 768 * 50257.

T=16 T=1024
Twelve layers 2.73 billion 212.6 billion
Output projection 1.24 billion 79.0 billion
Total 3.96 billion 291.6 billion

Everything else in the model (layer norms, GELU, softmax, additions) is a few operations per element of tensors with at most a few million elements: under 1% of the arithmetic at T=16 and a few percent at T=1024.

This is the single most important fact for the performance work. The model is, to a first approximation, 73 matrix products. A unit used throughout is GFLOP/s, billions of flops per second: how fast a matrix-product routine is. If the routine runs at 100 GFLOP/s, T=1024 takes about 2.9 seconds whatever else you do.

Note also the two attention products grow with T * T. At T=16 they are negligible (0.2% of flops); at T=1024 they are 13%.

3. Getting the model out of PyTorch

The compiler is written in C++, and the model lives in Python as a torch.nn.Module. This chapter covers the bridge: three short Python files under export/ that turn the model into two files the C++ side can read, and save the reference answers everything is later checked against.

3.1 Pinning down "the model" (export/model.py)

The Hugging Face GPT2LMHeadModel returns a rich object and can return cached state for fast generation. A compiler wants a pure function: one tensor in, one tensor out. So the model is wrapped:

class GPT2Logits(torch.nn.Module):
    def forward(self, input_ids):
        return self.gpt2(input_ids=input_ids, use_cache=False).logits

load_model() returns this in .eval() mode (which turns off dropout, a training-only randomization).

The same file defines the sequence lengths (16, 64, 256, 1024) and make_input_ids(seq_len), which produces fixed pseudo-random token ids from a seed. Everything in the project that needs the model or an input imports from this file: the exporter, the golden outputs, and every baseline in the benchmark. That is what guarantees all systems run the same network on the same input.

3.2 Tracing: torch.export

torch.export.export(model, (ids,)) runs the model's Python code once with an example input and records every tensor operation that happens. The result is an ExportedProgram: a flat list of operations with no Python control flow left. This is tracing.

Two properties of the result matter:

  • Shapes are fixed to those of the example input. That is exactly what this project wants (one compile per T).
  • Parameters are "lifted". The weights become extra inputs to the traced graph, and a separate table (the graph signature) records which input is which parameter.

The operations recorded are ATen operators. ATen is PyTorch's C++ tensor library; every torch.something call ends up as one or more ATen operators such as aten.addmm.default or aten.view.default. The suffix (default, Tensor, Scalar) is the overload: aten.mul.Tensor multiplies two tensors, aten.mul.Scalar multiplies a tensor by a Python number.

3.3 Decomposition

As traced, the graph uses 31 distinct operators, some of them high-level (layer_norm, dropout, transpose, masked_fill). Calling

core = exported.run_decompositions()

rewrites those into a smaller standard set called core ATen. After it the graph has 852 nodes using 37 distinct operators. docs/export_ops.md lists them with counts; the most common are

Operator Count What it is

Why decompose? A smaller operator set means less for the importer to implement. The price is that some structure is lost: GELU arrives as nine primitive nodes, and the causal mask as about forty. Chapter 6 puts that structure back where it helps.

The exporter immediately re-runs the decomposed program and compares it with the original model, refusing to continue if any logit differs by more than 0.001. The observed difference is about 0.0001, which is ordinary floating-point reordering (section 9.7).

3.5 The serializer (export/serialize.py)

This file writes what torch.export produced to disk. Its governing rule: it does not interpret anything. It records operator names and arguments exactly as PyTorch gave them. Every decision about what an operator means is made in C++, where it can be tested. The Python is only a transcription.

The weights file

artifacts/graphs/gpt2_weights.bin: every parameter tensor's raw bytes (little-endian 32-bit floats), one after another. 497 759 232 bytes.

  • Each tensor starts on a 64-byte boundary (padding bytes are inserted). 64 bytes is one cache line (chapter 9), so a tensor never shares a cache line with its neighbour.
  • Tied weights are stored once. The token embedding and output projection are the same tensor under two parameter names. The serializer notices that two parameters share a data pointer and gives both the same offset.
  • The file is written once and shared by all four sequence lengths. The script checks that every T produces the identical parameter table.

4. The graph IR and the importer

The graph IR is the compiler's first internal form of the model. It answers one question: what is computed? Nothing in it says how, in what loop order, or where in memory.

4.1 The design in one paragraph

A graph is a list of nodes in execution order. Each node applies one operator to the results of earlier nodes and produces exactly one tensor. Because a node produces exactly one value, a value is simply named by its node's position in the list: %29 is "the result of node 29". Every value has a fixed type: a dtype and a complete shape.

Three properties are worth names, because the rest of the compiler leans on them.

Static single assignment (SSA). Every value is defined exactly once and never changes. There is no "variable x that gets updated". The residual connection x = x + attention(...) in Python becomes a new value %42 = add(%41, %6); %6 still exists unchanged. With SSA, "where did this value come from?" always has one answer, which makes pattern matching (chapter 6) straightforward.

Purity. A node's result depends only on its inputs and its attributes. Nothing is modified in place and nothing has side effects. Consequences: a node nobody uses can be deleted; two nodes with the same operator and inputs compute the same thing and can be merged; a node whose inputs are constants can be computed at compile time. None of these would be safe if operations could modify shared state.

Static types. Every shape is known. The compiler can therefore check itself: after any transformation, the types must still be consistent.

4.2 The data structures (src/graph/ir.h)

enum class DType { F32, I64, Bool };
using Shape = std::vector<int64_t>;
struct Type { DType dtype; Shape shape; };

struct Node {
  Op op;                        // which operator
  Type type;                    // type of the value this node produces
  std::vector<ValueId> inputs;  // indices of earlier nodes
  Attrs attrs;                  // operator parameters that are not tensors
  std::string name;             // PyTorch's name, for humans only
};

struct Graph {
  std::vector<Node> nodes;          // in execution order
  std::vector<Constant> constants;
  std::vector<ValueId> inputs;      // the Input nodes
  std::vector<ValueId> outputs;
};

Attributes are an operator's non-tensor parameters: which axis to slice, the new shape of a reshape, the permutation. All operators share one Attrs struct with a field for each kind (axis, start, end, dims, keepdims, eps, to, index, causal, trans_b); each operator reads only its own fields. A separate struct per operator would be tighter, but one struct makes "are these two nodes identical?" a single comparison.

Constants come in two kinds, in one struct:

struct Constant {
  Type type;
  std::vector<std::byte> inline_data;  // small constants: the bytes themselves
  int64_t weights_offset = -1;         // weights: a position in the weights file
};

Scalars like 0.5 and small tables like the position indices 0..15 are inline. The 148 weight tensors are external: the graph holds only an offset. The compiler never loads weight data.

Two design decisions are visible here.

Many PyTorch spellings fold onto one operator. ATen has mm (matrix times matrix) and bmm (batched); both become MatMul, which treats any leading axes as a batch. view and unsqueeze both become Reshape. mul.Tensor and mul.Scalar both become Mul.

Composite operators are kept whole. Layer norm could be written with subtract, multiply, mean, and square root nodes. It is kept as one LayerNorm node because the loop generator can produce a much better loop nest for "layer norm" than for a chain of generic pieces. Gelu, the causal form of Softmax, and the trans_b form of the matrix products never come from the importer; graph passes create them (chapter 6).

4.4 Shape inference: infer_type

One function defines, for every operator, what type the result has given the input types and attributes, or that the combination is illegal:

Type infer_type(Op op, std::span<const Type> inputs, const Attrs& attrs);

Examples of its rules:

  • Add(a, b): dtypes must match and not be bool; result shape is the broadcast of the two shapes.
  • Eq(a, b): same, but the result dtype is Bool.
  • Reshape(a) with dims: the product of dims must equal a's element count.
  • Permute(a) with dims: dims must be a permutation of 0..rank-1; output axis i has the size of input axis dims[i].
  • MatMul(a, b): both f32, same rank of at least 2, equal batch axes, and a's last size equal to b's second-to-last. Result: batch axes, a's rows, b's columns.
  • Gemm(a, b, bias): rank 2 each, inner sizes match, bias length equals the number of result columns.

It is used in two places. Graph::add calls it to compute the type of each new node, so an ill-typed graph cannot be constructed. The verifier calls it again on every node of a finished graph and checks the stored type matches. One definition, used both to build and to check.

4.5 The printer and the verifier

print_graph (src/graph/printer.cpp) produces the text form shown in section 2.5; mlc dump prints it and mlc stats prints a count of nodes per operator.

verify_graph (src/graph/verifier.cpp) checks the invariants everything else assumes:

  • every input of a node is an earlier node (no use before definition, so no cycles);
  • every node's stored type is what infer_type derives;
  • every constant has exactly as many bytes as its type needs, or a valid offset;
  • inputs and outputs refer to real nodes.

It returns a list of problems; check_graph throws if the list is not empty. It runs after import, before every interpreter run, and after every optimization pass. A pass that produces a malformed graph is caught at once, with the pass's name in the error.

4.6 The importer (src/frontend/importer.cpp)

The importer reads graph.json and builds the graph IR. It is a table: one entry per ATen operator, each a small function that reads the node's arguments and adds IR nodes.

The symbol table

The central state is env_, a map from an exported node's name to the IR value or values that now stand for it. Most ATen nodes map to one IR value. A few are special:

  • A node that returns a tuple maps to several values. split_with_sizes (splitting qkv in three) becomes three Slice nodes. native_layer_norm returns (output, mean, rstd); only the first is ever used, so the other two slots are left empty.
  • getitem (pick element i of a tuple) creates no node. It looks the tuple up in env_ and binds its own name to the i-th value. If something asks for a slot that was left empty, that is an error.
  • clone and alias create no node. They exist in PyTorch because tensors are mutable; in an IR where values never change, "a copy of x" is just x.
  • _assert_tensor_metadata is a check PyTorch left in the graph. All dtypes are static, so it is evaluated during import and vanishes.

Parameters are created lazily

Parameters are recorded in a side table and only become Const nodes when something refers to them. The token embedding is exported under two names (tied weights), and only one is referenced.

Python-isms resolved at import

PyTorch arguments carry conveniences the IR does not have:

In PyTorch In the IR
negative axis (-1 means last) always 0..rank-1
-1 in a view shape ("work it out") the computed size
slice bounds that are negative, missing, or past the end plain start and end
a Python scalar operand (x * 0.5) a rank-0 Const node of x's dtype
full(shape, value) and full_like a scalar Const plus a Broadcast
cumsum of a bool tensor (returns int64) an explicit Cast, then CumSum
addmm(bias, a, b) Gemm(a, b, bias)

The scalar-operand rule is why the IR has more nodes (1062) than the export (852): every Python number becomes a constant node.

The full rule deserves a comment. A [1, 12, 1024, 1024] tensor of zeros would be 48 MB as a constant. As "scalar zero, broadcast" it costs 4 bytes in the graph, and a later pass can see at a glance that the whole tensor is zero.

No silent fallbacks

Two rules make the importer trustworthy:

  1. An operator not in the table is an error naming the operator. There is no "skip what you do not understand".
  2. An argument the lowering did not read is also an error. Each lowering function records which arguments it looked at. If the export passes, say, alpha=2 to addmm and the lowering ignored it, the compiler would compute a different function than PyTorch. (Arguments that only describe storage, like device, are on an explicit ignore list.)

Checking shape inference against PyTorch

Every node the importer creates is passed through check_against_export: the type our infer_type derived is compared with the type PyTorch recorded in the node's outputs field. The two were written independently, so agreement on every node of the real model, at four sequence lengths, is strong evidence the typing rules are right. A mismatch stops the import with both types in the message.

4.7 The JSON reader (src/support/json.*)

About 360 lines, written for this project instead of using a library. It is a recursive-descent parser (one function per kind of JSON value, each calling the others) producing a Value that is null, bool, integer, float, string, array, or object. It is strict (it rejects anything that is not valid JSON, including a bare Infinity) and it keeps integers and floats distinct, which the importer needs. Accessors like as_int() throw a json::Error if the value is the wrong kind, so a malformed graph file produces a clear message rather than a crash.

5. The reference interpreter and the idea of an oracle

5.1 Why build an interpreter inside a compiler

Before generating any code, the project built a program that executes the graph IR directly: walk the nodes in order, and for each one, run a plain C++ function that computes it. This is the reference interpreter (src/graph/interpreter.cpp, mlc run).

It is deliberately simple and slow. Its purpose is to be obviously correct, so that it can serve as a trustworthy answer key:

  • It proves the importer understood the model. If the interpreter's logits match PyTorch's, then the graph IR means what PyTorch meant.
  • It defines what each IR operator means, in runnable form.
  • Every later stage is tested against it. When an optimization pass rewrites the graph, run the interpreter on the graph before and after: the outputs must agree.
  • Constant folding (chapter 6) uses it as a calculator: to evaluate a piece of the graph at compile time, just interpret that piece.

5.2 The oracle chain

An oracle in testing is whatever tells you the right answer. This project has a chain of them, each checked against the one before:

PyTorch (golden logits)
   └─ graph interpreter, on the imported graph          [ctest: golden_T*]
        └─ graph interpreter, on the optimized graph    [ctest: optimized_T*]
        └─ loop interpreter, on small programs          [unit tests]
             └─ compiled code                           [unit tests, ctest: compiled_T*]

Each link compares two things that should compute the same function in different ways. A bug has to be present in both sides in exactly the same form to slip through.

The standard of correctness (STEERING.md section 6): on the fixed golden input, the largest absolute difference in any logit is at most 1e-3, and at every position the largest logit (the predicted next token) is the same one. Exact equality is impossible, because floating-point addition gives slightly different results depending on the order of operations (section 9.7), and every optimization changes that order. Observed differences are 1e-4 to 5e-4. For scale, logits are numbers roughly between -300 and 0.

5.3 Tensors at run time

struct Tensor {
  Type type;
  std::shared_ptr<std::byte[]> owner;  // keeps the memory alive; null if borrowed
  const std::byte* ptr;                // where the data is
};

A tensor either owns its memory (the interpreter allocated it) or borrows it (it points into the weights file, into an inline constant, or at the caller's input). shared_ptr is a reference-counted pointer: the memory is freed when the last tensor pointing at it goes away. This lets Reshape cost nothing: the result is a new Tensor with a different type and the same owner and ptr.

5.4 One loop to rule the elementwise and layout operators

Most operators are some version of "for every element of the output, read one element from each input". What differs is which input element. The interpreter has one generic loop for all of them, strided_loop, built on strides (section 2.1).

Broadcasting as stride 0. To read input in as if it had the larger output shape, give it a stride of 0 along every axis where it has size 1 (or no axis). Stepping along that output axis then does not move through the input at all, so the same element is read again. That is all broadcasting is.

The odometer. strided_loop visits every index of the output shape in row-major order, like a car's odometer: bump the last digit; when it overflows, reset it and carry into the next digit. Alongside the index it maintains, for each input, the current linear offset under that input's strides. Each step calls body(output_position, input_offsets).

With that:

Operator Input strides
Add, Mul, Eq, Where, ... each input's broadcast strides
Broadcast the input's broadcast strides
Permute the input's strides, reordered by the permutation
Slice the input's own strides, starting from an offset

Permute is the instructive one. If output axis d is input axis dims[d], then one step along output axis d should move through the input by the stride of input axis dims[d]. So the permuted strides are just the input strides shuffled.

A helper, by_dtype, instantiates the same generic code for float, int64_t, and uint8_t (bools are stored as one byte), so each operator is written once.

5.5 The remaining operators

  • Gather (x[i0, i1, ...]): for each position of the (broadcast) index tensors, compute an offset into x from the loaded indices and copy the remaining axes of x as one block. An index out of range is an error, not a wild read.
  • Concat: copy runs of each input in turn with memcpy.
  • CumSum: each element is its input plus the output one step back along the axis.
  • ReduceAny: OR along one axis.
  • MatMul / Gemm: see below.
  • LayerNorm: the formula of section 2.3, per row. The sums are accumulated in double so the reference's own rounding error is far below the tolerance it is used to check.
  • Softmax: computed as exp(x_j - max) / sum(exp(x_i - max)). Subtracting the row maximum first changes nothing mathematically (the factor cancels) but keeps every exponent at or below zero, so exp cannot overflow. A row that is entirely -inf gives 0/0 = NaN, the same as PyTorch.
  • Gelu, causal Softmax, and the trans_b products were added in M3 and M4 when passes began producing them.

The first loop interchange of the project

The definition of a matrix product, C[i][j] = sum over p of A[i][p] * B[p][j], suggests three loops in the order i, j, p. The interpreter uses i, p, j:

for (i ...) for (p ...) { float a = A[i*k + p]; for (j ...) C[i*n + j] += a * B[p*n + j]; }

With j innermost, the inner loop walks along a row of B and a row of C, both consecutive in memory, and A[i][p] is a constant. In the order i, j, p the inner loop would walk down a column of B, jumping n elements per step and touching a new cache line each time. Same arithmetic, several times faster. Chapter 10 is this idea taken to its conclusion.

5.6 Freeing values: liveness

At T=1024 the model's intermediate tensors add up to 6.7 GB. They are not all needed at once. A value is live from when it is computed until the last node that reads it; after that it is dead and its memory can be reused.

The interpreter does the simplest version: before running, count how many times each value will be read (uses_left). After each node runs, decrement the counts of its inputs; when a count reaches zero, drop the tensor. With that, peak memory at T=1024 is 363 MB instead of 6.7 GB.

The interpreter reports both numbers (mlc run --profile). The peak figure became the target that the compiler's memory planner (chapter 7) had to beat.

6.1 Why rewriting is safe here

Chapter 4 set this up. Values are defined once and never change (SSA), and nodes are pure. So the statement "node v computes the same tensor as value w" has an unambiguous meaning, and if it is true, every user of v can be pointed at w instead with no other consequences. Nothing else can observe the difference. All six passes are instances of that one move.

6.2 The rewriting engine

using RewriteRule = std::function<ValueId(Graph& out, const Node& n, const Constant* constant)>;
Graph rewrite(const Graph& g, const RewriteRule& rule);

rewrite never edits a graph in place. It walks the old graph in order and builds a new one:

  1. Take the next old node. Translate its inputs to the corresponding values of the new graph (a table remap records, for each old node, which new value stands for it).
  2. Call the rule with the new graph and this translated node.
  3. The rule either returns a value of the new graph that should stand for this node, or returns "no value", in which case the node is copied unchanged.
  4. Record the answer in remap.

Two consequences of this design are worth understanding.

A rule sees operands that have already been rewritten. By the time the rule looks at a node, its inputs are values in the new graph, already simplified. So a chain collapses in one sweep: for reshape(reshape(reshape(x))), when the outermost reshape is visited its operand is already a single reshape of x.

A rule may add new nodes and may leave garbage behind. If a rule replaces a node by something else, the nodes that only fed the old node are still copied into the new graph, now with no users. The engine does not clean them up. Dead code elimination does.

The engine also checks that the replacement has exactly the type of the node it replaces, and throws if not. A rule cannot accidentally change a shape.

6.3 Dead code elimination (DCE)

A node is dead if no output depends on it. eliminate_dead_code computes liveness backwards: mark the graph outputs live; walk the nodes from last to first; when a live node is reached, mark its inputs live. Because every user comes after the values it uses, one backward walk is enough. Then copy only the live nodes into a new graph.

Graph inputs are always kept, even if unused: they are part of the function's signature.

DCE runs after every other pass. That is why the table above charges each pass for everything it made removable: the pass rewires, DCE sweeps.

6.4 simplify: local cleanups (removes 111 nodes)

Each rule looks at one node and at most its immediate operands. No analysis is needed.

Pattern Replacement In GPT-2

Reshape to the same shape the operand
Reshape(Reshape(x)) one Reshape(x), or x if the final shape is x's view chains

Permute(Permute(x)) one composed Permute(x), or x if they cancel the head merge is three permutes in a row

Composing permutations. The outer permute says "my axis i is the middle value's axis outer[i]"; the inner says "my axis k is x's axis inner[k]". So the result's axis i is x's axis inner[outer[i]]. That one line of reasoning is the whole rule.

6.5 fold: constant folding (removes 49 nodes)

If all of a node's operands are known at compile time, compute the node now and replace it by a constant. Because the engine visits nodes in order and operands are already folded, a whole constant subgraph collapses from its leaves upward, one node at a time.

How a node is evaluated: build a tiny graph containing only that node and its constant operands, and run the reference interpreter on it. No second implementation of the operators is needed.

What it folds in GPT-2: the position indices, and the roughly forty nodes that build the causal attention mask from arange, cumsum, and comparisons.

Three limits, each with a reason:

  • External weights are never folded. Folding permute(weight) would require reading 498 MB of weights into the compiler and writing the result into the generated code. The rule from chapter 3 stands: weight bytes stay in the weights file. (Chapter 7's staging handles these cases differently.)
  • Broadcast is never folded. It would turn a 4-byte scalar into a full tensor, and destroy the information that the tensor is uniform.
  • Results over 1 MB are not folded. At T=1024 the causal mask is [1,1,1024,1024] floats, 4 MB. Leaving it unfolded is fine: the attention pass below recognizes it anyway and then it becomes dead.

6.6 cse: common subexpression elimination (removes 122 nodes)

Two nodes with the same operator, the same operands, and the same attributes compute the same value. Keep the first, point users of the second at it.

The implementation is value numbering. For each node build a key: operator, result type, operand ids, attributes (for a constant: its bytes or its weights offset). Keep a hash map from key to the value already created for it. If the key has been seen, return that value; otherwise copy the node and record it.

The subtle part is that operand ids in the key are ids in the new graph, which have already been deduplicated. So two identical subtrees get identical keys from the bottom up, without ever comparing trees.

In GPT-2 almost everything it merges is duplicate scalar constants (every layer has its own 0.5, its own 3.0, its own copy of the attention scale) and, before fold, per-layer copies of the mask. It removes 122 nodes but only 11 kernels' worth of actual work, since constants never had code.

A pitfall worth remembering. Whenever a new attribute is added to Attrs, it must be added to the CSE key. Otherwise two nodes that differ only in that attribute would be merged. causal and trans_b were both added to the key when they were introduced.

6.7 gelu: recognizing GELU (removes 89 nodes)

The export spells GELU (section 2.3) as nine nodes per layer:

half  = mul(h, 0.5)
cube  = pow(h, 3.0)
inner = mul(add(h, mul(cube, 0.044715)), 0.7978845608)
out   = mul(half, add(tanh(inner), 1.0))

Each is a full pass over a [1, T, 3072] tensor with its own output buffer. The pass replaces the group by one Gelu(h) node, which the loop generator turns into a single pass.

How pattern matching works. The rule fires on the last node of the pattern, the final mul, and walks backwards through its operands checking each step:

  1. Is one operand mul(h, 0.5)? Remember h.
  2. Is the other add(t, 1.0), with t a tanh?
  3. Is the tanh's operand mul(s, 0.7978845608)?
  4. Is s an add with h as one operand? Call the other c.
  5. Is c equal to mul(cube, 0.044715), with cube = pow(h, 3.0)?
  6. Is it the same h everywhere?

If every check passes, emit Gelu(h). The eight nodes above the final mul now have no users and DCE removes them.

Details that make it robust:

  • Multiplication and addition commute, so each step tries both operand orders.
  • Constants are compared with a small tolerance, because 0.7978845608028654 arrives rounded to a 32-bit float.
  • Lookalikes are rejected: a wrong constant, or a cube of a different tensor, fails a check and the nodes are left alone. There are tests for exactly these.

Matching is done on the compiler's own IR after simplify and cse, not on raw ATen. The earlier passes put the graph in a more regular form, which makes the pattern less fragile.

6.8 attention: the causal softmax (removes 76 nodes)

Each attention layer exports as:

s    = add(scores, mask)                    mask is 0 where j <= i, -inf where j > i
p    = softmax(s, last axis)
dead = not(reduce_any(not(eq(s, -inf))))    "is this whole row -inf?"
out  = where(dead, zeros, p)                such a row would be NaN; make it 0

Two observations make all of this redundant:

  1. The guard can never fire. With a causal mask, row i always keeps column i (a position can attend to itself). So no row is entirely masked and dead is always false. (This assumes the scores themselves are finite.)
  2. Adding -inf before exp is a roundabout way of leaving columns out. exp(-inf) = 0, so the masked columns contribute nothing to the sum and get probability 0.

So the whole group equals "softmax of row i over columns 0..i only, with zeros after". The pass replaces it by one Softmax node with the attribute causal=true, applied directly to the raw scores. That does half the exponentials and needs no mask in memory at all.

Recognizing the mask by value. The pass does not try to recognize the forty-node computation that produces the mask. It asks the function evaluate_constant to compute the mask at compile time (by interpreting the part of the graph it depends on), and then checks the resulting numbers: is it [1, ..., 1, T, T] with 0 on and below the diagonal and -inf above? Whatever computes the mask, if it evaluates to that pattern, the rule fires. This is why it works at T=1024 even though fold declined to fold the 4 MB mask.

6.9 layout: transposed matrix products (adds 71 nodes)

This pass was added in M4 and only makes sense together with chapter 10, so here is just what it does.

Every matrix product a @ b is rewritten to take its second operand already transposed. The node gets the attribute trans_b, and its second input becomes bt = transpose(b), with shape [n, k] instead of [k, n]. The value computed is the same.

The reason: element (i, j) of the product is then the dot product of row i of a and row j of bt. Both are contiguous runs of memory, which is the form the fast kernel wants.

Naively this inserts a transpose in front of every product. The pass builds each transposed operand with a helper that looks for cheaper ways:

  • The operand is already a transpose of something: use that something. This cancels the transpose on the output projection (it was transpose(embedding table) to begin with) and on q @ transpose(k) in attention.
  • The operand is x * scalar: then its transpose is transpose(x) * scalar. Moving the transpose inward lets it meet, and cancel, a transpose applied before the scaling. GPT-2 scales k after transposing it, so this rule is what makes the attention case cancel.
  • Otherwise: insert a real Permute.

What is left: 48 transposes of dense-layer weights (which chapter 7's staging computes once at load time, not per call) and 12 transposes of the attention value matrix (small, per call). The node count goes up by 71, which is fine; the count was never the goal.

6.10 The pipeline and its switches

optimize(g, options, stats) runs DCE, then each enabled pass followed by DCE and the verifier, recording node counts before and after. If the verifier fails after a pass, the error names the pass.

Every pass can be turned off by name: mlc compile ... --disable gelu,cse. --disable all turns everything off. This is how the ablation tables (chapter 12) are produced: build the model with one thing off, measure, compare.

6.11 What the graph passes bought

Measured, not assumed (chapter 12 has the tables):

  • Graph size: 1062 nodes to 615 (before layout). Kernels: 541 to 258. The generated C++ compiles in a third of the time.
  • Memory: together with memory planning (chapter 7), the arena at T=1024 went from 6453 MB to 158 MB.
  • Speed: nothing measurable. Matrix products are over 96% of the run time and these passes do not touch them. The passes removed about a quarter of the remaining work, and a quarter of 3% does not show. This was a surprise at the time and is one of the honest findings of the project: at this model's shape, graph-level optimization is about memory and cleanliness, not time.

The graph IR says %29 = matmul(%27, %28). To run that, something has to say: these are the loops, this is the order they nest in, and these are the memory addresses they read and write. That is the loop IR (src/loop/ir.h). Translating the graph into it is lowering (src/loop/lower.cpp).

7.1 The whole language

Three kinds of statement:

Statement Meaning
For(var, extent, body) run body with var = 0, 1, ..., extent-1
Store(buffer, indices, value) buffer[indices] = value
Block(stmts) run statements in order

Nine kinds of expression:

Expression Meaning
IntImm, FloatImm a constant
Var a loop variable
Load(buffer, indices) read buffer[indices]
Binary(op, a, b) + - * / max == != <= & |
Not(a) logical not
Call(fn, args) exp, tanh, pow, sqrt
Select(c, a, b) c ? a : b
Cast(type, a) convert between float, int, bool

That is all. A matrix product in this language, printed by mlc loops:

kernel matmul  # %2
  for i0 in 0..2:
    for i1 in 0..3:
      v2[i0, i1] = 0
      for i2 in 0..4:
        v2[i0, i1] = (v2[i0, i1] + (v0[i0, i2] * v1[i1, i2]))

Design choices in the language

No scalar variables. There is no way to write sum = 0; ... sum += x. A running sum has to live in memory: load it, add, store it back (the last line above). This looks wasteful, and in generated code it would be if left that way. The reason is analysis: with no hidden variables, every way one iteration can affect another is a visible load or store of a named buffer. The legality checks in chapter 10 depend on that. Registers come back at the very end, in generated code.

Multi-dimensional indices. Accesses are written v2[i0, i1], one index per axis, and only flattened to a single offset when C++ is printed. Keeping the indices separate is what lets the analysis say "this loop variable appears only in axis 1".

Loop extents are constants, or simple expressions of outer loop variables. Shapes are static, so nearly every loop has a constant trip count. The one exception is the causal softmax, whose inner loops run to i + 1.

Loops carry a "kind". Serial, vectorized, or parallel. A fresh lowering is all serial; chapter 10 changes kinds. The kind never changes what a loop computes.

Expressions are immutable and shared. An Expr is held by shared_ptr<const Expr>, so a subexpression can appear in many places without copying, and no transformation can corrupt another's tree.

Constructors check and tidy. binary(...), load(...) and friends throw if operand types do not match (adding an int to a float, a non-integer index). They also fold integer constants (x + 0, x * 1, 2 * 3) so that index arithmetic stays readable.

7.2 Buffers and storage

A buffer is a named, typed, shaped view of some memory:

struct Buffer { std::string name; DType dtype; Shape shape; Storage storage; int64_t offset; int32_t index; };

storage says where the bytes live at run time:

Storage Meaning Writable
Arena scratch memory owned by the runtime, at byte offset yes
Weights the memory-mapped weights file, at byte offset no
Persistent memory filled once when the model loads, at byte offset by init kernels only
Input the caller's input number index no
Output the caller's output number index yes
Inline a small constant table carried in the generated code no

The arena is one big block of scratch memory. Every intermediate tensor is a slice of it at a fixed offset decided by the compiler. At run time there is no malloc: the runtime allocates the arena once and kernels use offsets into it.

Two buffers may view the same bytes. That is how Reshape costs nothing: the reshaped value gets a second Buffer with a different shape and the same storage and offset, and no code is generated for it at all.

A kernel is the loop nest for one graph node, with a name for profiles. A program is the list of buffers, the kernels in order, and the sizes of the arena and persistent regions.

7.3 Lowering each operator

One function per kind of operator in lower.cpp. They share a few helpers:

  • nest(shape, body): one loop per axis of shape, outermost first. An axis of size 1 gets the constant index 0 and no loop, so a [1, 16, 768] tensor produces two loops, not three.
  • read(v, idx): a load of value v. A rank-0 inline constant is emitted as a literal, so the code says x * 0.5, not "load from a one-element table".
  • read_broadcast(v, out_idx): read v at an index of a larger broadcast shape. Where v has size 1 the index is the constant 0. This is the interpreter's stride-0 trick done at compile time: the loop variable simply does not appear in the access. A broadcast therefore costs nothing in the loop.

Add, Mul, Tanh, Where, Cast, ... out[i...] = f(a[i...], b[i...]) with broadcasting
Gelu the same, with the GELU formula as one expression; x^3 is two multiplies, not a call to pow

CumSum is worth a look because it shows the IR making a property visible. Its second loop reads out[j], which the previous iteration wrote. That is a loop-carried dependence: the iterations must run in order. Chapter 10's analysis will find it by looking at exactly this load and store.

The matrix products

There are two lowerings, depending on whether the layout pass (section 6.9) ran.

Without layout (operand B is [k, n]), the loop order is i, p, j, the same one the interpreter uses:

for i: { for j: C[i,j] = init
         for p: for j: C[i,j] = C[i,j] + A[i,p] * B[p,j] }

With layout (operand Bt is [n, k]), each element is a dot product:

for i: for j: { C[i,j] = init
                for p: C[i,j] = C[i,j] + A[i,p] * Bt[j,p] }

init is 0 for MatMul and bias[j] for Gemm. In the second form the lowering also records in the kernel which loop variable is i, which is j, and which is p, and a signature string such as gemm [16,768] x [2304,768]^T. The scheduler and autotuner use both.

The causal softmax

For row i, only columns 0..i take part. The loops' extent is the expression i + 1, and a final loop writes zeros to the columns after i. Half the exponentials of the full square are never computed. (In M3 this was written with a Select inside a full-length loop, because the IR did not yet have non-constant extents. M4 added them.)

7.4 Memory planning

Where should each value's buffer go in the arena? The naive answer (M2) gives every value its own slice. At T=1024 that is 6453 MB, and the first call spends 40 seconds just having the operating system hand over fresh pages.

Memory planning (M3) reuses slices. It is done during lowering by three mechanisms.

Liveness

Kernels run in node order, so a value's lifetime is an interval: from its own node index to the index of the last node that reads it. Two values can share memory exactly when their intervals do not overlap.

analyze() computes last_use for every value in one pass over the graph. One subtlety: a Reshape does not own bytes. It is the same bytes as its operand. So each value has a root, the value that actually owns its memory, and a read of the reshaped value counts as a read of the root.

In-place reuse

An elementwise kernel reads in[i] and then writes out[i], and never looks at in[i] again. If this kernel is the last reader of that input, the output can simply take over the input's memory: by the time out[i] is stored, in[i] has been used.

in_place_operand checks the conditions:

  • the operator is one of those that read each element before writing the same element (Add, Sub, Mul, Pow, Tanh, Gelu, And, Not, Where, LayerNorm, Softmax);
  • this node is the operand's last reader;
  • the operand has exactly the node's type (same shape and dtype);
  • no other operand views the same bytes under a different shape (a broadcast or reshaped second view would read elements already overwritten).

When it applies, no new memory is allocated at all. A residual add writes its result over one of its inputs. A test checks that the model's output is bit-for-bit identical with planning on and off.

The arena allocator

For values that need fresh memory, ArenaPlanner hands out byte ranges at compile time:

  • It keeps a free list: ranges that were released, ordered by offset.
  • alloc(bytes) uses best fit: the smallest free range that is large enough. Taking a snug block leaves the big ones for big tensors still to come. Whatever is left of the range goes back on the list.
  • If nothing fits and the last free range touches the end of the arena, the arena grows by only the difference.
  • release puts a range back and coalesces it with free neighbours, so two small adjacent holes can later serve one large request.
  • Every range is rounded up to 64 bytes, so every buffer starts on a cache-line boundary.

After each node is lowered, release_after frees its temporaries and every operand it was the last reader of.

The planner reports two numbers: the arena size reached with reuse, and the total it would have been without.

T=16 T=1024
No reuse (M2) 192 MB 6453 MB
With planning (M3) 154 MB 158 MB
With planning, after M4 0.3 MB 72 MB

After M3 the arena was almost the same at every T because one buffer set it: the 154 MB transposed copy of the embedding table. M4's layout pass removed that buffer.

Outputs

A value the caller wants back is computed straight into the caller's buffer (Storage::Output) when possible. When it is not (the output is a graph input, a constant, or the same value twice), a small copy kernel is added at the end.

7.5 Staging: compute it once, at load time

Some values depend only on the weights and on constants, not on the caller's input. They are the same on every call. Computing them on every call is waste.

Constant folding (section 6.5) cannot handle them: the compiler does not have the weight bytes. But the runtime does, once it has opened the weights file.

So lowering sorts every value by when it becomes known:

Stage What Where it is computed
compile time inline constants by the compiler (fold)
load time weights, and anything computed only from weights and constants once, when the model is opened
run time anything downstream of a graph input on every call

The rule (stage()): an Input is run-time; any other node is load-time if all of its inputs are load-time. A load-time node's kernel goes into a separate list, the init kernels, and its result goes into persistent memory, which is never freed or reused.

This is sometimes called binding-time analysis, or just hoisting. It is constant folding performed by the runtime.

In GPT-2 it applies to 49 values: the 48 transposed dense-layer weights that layout introduced, and the position-embedding lookup (wpe[0..T-1], which depends only on T). They cost 340 MB of persistent memory and about 0.1 s at load.

7.6 The loop interpreter and verifier

run_program (src/loop/interpreter.cpp) executes a program by walking its tree. It runs the init kernels, then the kernels. Every loop runs serially in order, whatever its kind. Every index is checked against the size of its own axis, which is stricter than checking the flat offset: an index that runs off one axis but lands inside the buffer is still a bug, and is caught.

verify_program (src/loop/ir.cpp) checks structure: each access has as many indices as the buffer has axes; indices are integers; a stored value has the buffer's dtype; nothing stores to read-only storage; only init kernels write persistent memory and they never read caller inputs; loop variables are used only inside their loops and not bound twice in a nest; every buffer fits inside its region.

8. Code generation and the runtime

The loop IR is still a data structure inside the compiler. This chapter covers the last steps: printing it as C++, compiling that into a shared library, and the small handwritten runtime that the library contains and that actually runs the model.

To follow along:

8.1 Why emit C++ and not machine code

A compiler normally ends by producing machine instructions. This one ends by producing C++ source text and then running clang++ on it. Reasons:

  • Turning arithmetic into good machine code (choosing instructions, assigning registers) is a large, well-solved problem. Using an existing compiler for it leaves the project free to spend its effort on the parts that are specific to neural networks.
  • The output is readable. When something is slow or wrong you can open model.cpp and look.
  • It is portable to any machine with a C++ compiler.

The division of labour is: this compiler makes every decision that requires knowing the program is a neural network (what to fuse, where memory goes, which loops to tile or vectorize). clang++ handles the last mile. Chapter 10 shows where that line had to be moved: clang would not vectorize the loops on its own, so the project emits SIMD instructions explicitly.

8.2 What the generated file contains

For a program with N kernels, model.cpp has:

  1. Includes, and one helper, mlc_max.
  2. Inline constants as static arrays, for example const int64_t inline_0[16] = {0, 1, ..., 15};. Only small tables. Weights are never written into the code.
  3. One pair of functions per kernel (below).
  4. Two tables: the init kernels and the per-call kernels, each entry holding the operator name, a label, and a function pointer.
  5. mlc_gen_model, a struct describing the model: arena size, expected weights file size, persistent memory size, the sizes of each input and output, and the two tables. This struct is the entire interface between generated code and the runtime.

8.3 One kernel in C++

A serial kernel is a direct transcription. An Add of two [1, 16, 768] tensors:

// %6 add_1
static void k1_add_body(const float* __restrict v2, const float* __restrict v5, float* __restrict v6) {
  for (int64_t i0 = 0; i0 < 16; ++i0) {
    for (int64_t i1 = 0; i1 < 768; ++i1) {
      v6[((i0 * 768) + i1)] = (v2[((i0 * 768) + i1)] + v5[((i0 * 768) + i1)]);
    }
  }
}

void k1_add(char* arena, const char* weights, char* persist,
            const void* const* inputs, void* const* outputs) {
  k1_add_body((const float*)(arena + 0), (const float*)(persist + 0), (float*)(arena + 49152));
}

(Simplified for illustration: the offsets are made up, and in the real file the inner loop is vectorized, section 10.6.)

Flat indexing. The IR's v6[i0, i1] becomes one subscript by Horner's rule (section 2.1): ((i0 * 768) + i1). flat_index builds that expression.

Float literals are printed with nine significant digits (0.100000001f), which is always enough for a 32-bit float to read back as exactly the same value. Infinity is printed as INFINITY.

Why two functions. The outer function has the fixed signature the runtime calls: pointers to the three memory regions and to the caller's arrays. It turns offsets into typed pointers. The inner function receives those pointers as parameters marked __restrict. The reason is in section 9.6; briefly, __restrict is a promise to the C++ compiler that these pointers do not overlap, and C++ compilers only honour that promise on function parameters.

Pointer grouping. Buffers that are the same bytes (a value and its reshaped view; an in-place kernel's input and output) share one pointer. A pointer is marked __restrict only if no other pointer of the kernel reaches memory that is written through it. The memory plan from chapter 7 is what makes this decidable: the compiler knows every buffer's exact byte range.

8.5 The runtime (runtime/mlc_runtime.{h,cpp})

About 280 lines of handwritten C++. It owns resources and drives kernels; it contains no numerical code. Its interface is plain C, so that Python can call it directly:

// plus queries: mlc_arena_bytes, mlc_num_kernels, mlc_kernel_op, mlc_input_bytes, ...

mlc_open

  1. Map the weights. mmap asks the operating system to make a range of addresses stand for the file's contents. Nothing is read at that moment. Pages are fetched from disk the first time they are touched, the memory is shared with the system's file cache rather than copied, and a weight that is never read never costs anything. The file's size is checked against what the model was compiled for.
  2. Allocate the arena with an anonymous mmap rather than malloc. The system hands out zeroed pages lazily, so arena the model never touches costs no physical memory, and the start is page-aligned.
  3. Allocate persistent memory the same way.
  4. Run the init kernels (section 7.5), which fill persistent memory from the weights.

mlc_run

A loop over the kernel table, calling each function in order with the three region pointers and the caller's input and output arrays. That is the whole inference "engine": an array of function pointers.

mlc_run_profiled does the same and times each call. mlc exec --profile uses it to print time per operator, taking each kernel's best time over several runs.

9. What makes code fast on a CPU

Chapter 10 transforms loops to make them fast. Every transformation there exists because of a specific property of the hardware. This chapter is those properties. Nothing here is specific to the project; it is the background that the rest assumes.

The machine: an Apple M2. Four performance cores (fast) and four efficiency cores (slow, low power). The project targets the performance cores.

9.1 The unit of measurement

A matrix product of [m, k] by [k, n] does 2 m k n floating-point operations (flops). GFLOP/s is billions of flops per second. It measures a matrix-product routine independently of the matrix sizes.

Reference points on this machine (AC power, one performance core):

What GFLOP/s
The naive loop from M2, in the model about 8
This project's final kernel, in the model 80 to 100
The same kernel on data that fits in cache about 100
Theoretical limit of one core's SIMD units about 110
Apple Accelerate (uses other hardware) 400 to 1400

9.2 SIMD

SIMD (single instruction, multiple data) instructions operate on several numbers at once. On this CPU the SIMD instruction set is NEON. A NEON register is 128 bits wide and holds four 32-bit floats. One instruction adds, multiplies, or loads all four lanes together.

In C++ these instructions are reachable as intrinsics: functions that the compiler turns into exactly one instruction.

float32x4_t a = vld1q_f32(p);          // load 4 floats from address p
float32x4_t b = vld1q_f32(q);
float32x4_t c = vfmaq_f32(acc, a, b);  // acc + a*b, on all 4 lanes
vst1q_f32(r, c);                       // store 4 floats
float s = vaddvq_f32(c);               // add the 4 lanes into one float

There are 32 NEON registers. That number will matter.

Vectorizing a loop means rewriting it to process four iterations per step using these instructions, plus a scalar loop for the leftover iterations when the trip count is not a multiple of four.

FMA (fused multiply-add) computes a + b*c as one instruction with one rounding at the end. It is both faster and slightly more accurate than a multiply followed by an add. A matrix product is nothing but FMAs.

9.3 Pipelines: latency and throughput

A modern core does not execute one instruction at a time. It has several execution units and runs instructions as soon as their inputs are ready, out of order. Two numbers describe an instruction:

  • Latency: how long from inputs ready to result ready. For an FMA on this core, about 3 to 4 clock cycles.
  • Throughput: how many can be started per cycle. This core has four SIMD units, so four FMAs per cycle.

The gap between those two numbers is the key to the fast matrix product.

Consider a dot product with one accumulator:

acc = acc + a[p] * b[p]      for p = 0, 1, 2, ...

Each FMA needs the previous acc as input. They form a dependency chain: the next cannot start until the last finishes. The loop runs at one FMA per latency, about one per 3 cycles, while the hardware could start four per cycle. Eleven twelfths of the capacity is idle.

The fix is to run many independent chains at once. With 16 or more separate accumulators, each waiting on its own previous value, there is always something ready for every unit on every cycle.

This was measured directly in a hand-written experiment (M4): a kernel with 1 accumulator ran at 4.8 GFLOP/s, with 4 at 17.5, with 8 at 32, and with 16 or 20 at 59, where it stopped improving. (Those absolute numbers were taken in Low Power Mode, section 9.9. The ratios are what matter.)

The theoretical peak follows: 4 FMAs per cycle, each doing 4 multiplies and 4 adds, at about 3.5 billion cycles per second, is 4 * 8 * 3.5 = 112 GFLOP/s.

9.4 Caches

Main memory is slow relative to the core: a read from it takes on the order of a hundred cycles. So the CPU keeps recently used data in small fast memories called caches.

Level Size (performance core) Roughly how long a read takes
L1 data cache 128 KB 3 to 4 cycles
L2 cache 16 MB (shared by the four performance cores) about 15 cycles
Main memory gigabytes 100 cycles or more

Caches work in lines of 64 bytes (16 floats). Touching one byte brings in its whole line.

Three consequences drive everything in chapter 10:

  1. Sequential access is cheap. Reading memory in order touches each line once, and the CPU's prefetcher notices the pattern and fetches lines ahead of time. Jumping around defeats both.
  2. Reuse must happen while data is still in cache. If a loop needs the same data many times, arrange for those uses to be close together in time, so the data is still in L1. This is locality.
  3. Memory bandwidth is finite. Even perfectly sequential reads from main memory arrive at a limited rate, a few tens of gigabytes per second for the whole machine. A computation that does little arithmetic per byte it reads is limited by this, not by the core. Section 12.6 is an example.

A cache is also divided into sets, and each address can only live in one set, which has a handful of slots (for a 128 KB cache with 8 slots per set, addresses a multiple of 16 KB apart compete for the same 8 slots; the exact arrangement on this core was not measured). Accessing a matrix column whose elements are spaced by a "round" number of bytes can therefore thrash a cache that is nowhere near full. This is one of the classical reasons high-performance libraries copy data into contiguous buffers ("packing") before multiplying, and one reason this project's kernel is designed to read only along rows.

9.5 Why loop order and blocking matter

Take C[i][j] += A[i][p] * B[p][j] with matrices too large for the cache.

  • With p innermost, the loop walks down a column of B, one element per row, jumping n floats each step. Every step is a new cache line.
  • With j innermost, it walks along a row of B and a row of C. Sequential.

That is loop interchange (section 5.5 used it already).

Blocking (also called tiling) goes further. If a loop sweeps over a large array many times, split the array into blocks that fit in cache and finish all the work on one block before moving to the next. Each block is then loaded once and used many times while it is in L1, instead of being reloaded on every sweep.

9.6 Aliasing

Two pointers alias if they can refer to the same memory. Consider

for (j ...) C[j] = C[j] + a[0] * B[j];

Can the compiler load a[0] once before the loop? Only if no store to C[j] can change a[0]. If C and a are just two pointers into unknown memory, it cannot know, and must reload a[0] on every iteration. Worse, it cannot vectorize: processing four iterations at once changes the result if the store in iteration 1 was supposed to affect the load in iteration 2.

restrict (spelled __restrict in C++) on a pointer parameter is the programmer's promise that, during the function, memory written through that pointer is not reached through any other. With it the compiler can assume no overlap.

This project's compiler knows its buffers do not overlap, because its own memory planner placed them. So it emits __restrict (the noalias switch). It has to be on function parameters because clang ignores restrict on local variables.

9.7 Floating point is not associative

A 32-bit float holds about seven significant decimal digits. Every operation rounds its result to the nearest representable value. Because of that rounding,

(a + b) + c    and    a + (b + c)

can differ in the last digit. Adding 768 numbers in a different order gives a slightly different sum.

Two consequences:

The C++ compiler may not reorder float additions. The language requires the result you would get by doing the operations in the written order. A vectorized sum adds lanes separately and combines them at the end, which is a different order. So clang will not vectorize a loop like sum += x[i] unless you pass -ffast-math, which permits reordering everywhere. This is why "transposed layout without our own vectorizer" was a large slowdown in the M4 ablation: a dot product is a float sum, and clang ran it one element at a time.

The project's vectorizer reorders deliberately. It is allowed to because the correctness criterion is a tolerance (1e-3), not bit equality. The reordering is a decision made in the loop IR (the loop is marked vectorized), visible in mlc loops, and limited to sums and maxima. The differences it causes are around 1e-4 on logits of magnitude 100, which is the expected size for seven-digit arithmetic.

Other facts used in the project: infinity and NaN ("not a number", the result of 0/0) are ordinary float values; exp(-inf) = 0; any comparison with NaN is false.

9.8 Threads

Four performance cores can run four pieces of work at once. To use them, a loop whose iterations are independent is split into four ranges, one per thread. Things that limit the gain:

  • Starting and waking threads costs time. Waking a sleeping thread through the operating system takes tens of microseconds, comparable to an entire small kernel at T=16. The runtime keeps its threads alive and lets idle ones spin briefly before sleeping (section 10.9).
  • Shared resources. The four cores share the L2 cache and the memory bus. A computation limited by memory bandwidth does not speed up four times.
  • No thread affinity on macOS. A program cannot pin a thread to a core. It can only request a high quality-of-service class, which makes the scheduler prefer performance cores.
  • Amdahl's law. If a fraction of the work is not parallel, it bounds the speedup.

Measured: four threads give 3.0 to 3.6 times the speed on the large matrix products in isolation, and 2.1 to 3.3 times on the whole model.

9.9 The power state of a laptop

This cost a full day of misleading numbers, so it has its own section.

On battery with Low Power Mode on, macOS caps the performance cores at roughly half their clock speed and throttles sustained multi-core load. In that state:

  • One core peaked at 59 GFLOP/s instead of about 100.
  • Four-thread runs at T=1024 took 1.6 s the first time and 3.2 s on later runs, as throttling set in.
  • Because the core was slow relative to memory, memory effects were hidden. In Low Power Mode this project's kernel measured faster than ONNX Runtime's on large products; at full speed it is 9% slower. The conclusion reversed.

Every result file in bench/results/ records the power state. Numbers are only compared within one session.

9.10 Why PyTorch is so much faster on this machine

PyTorch on macOS sends matrix products to Apple's Accelerate library. In M0 it measured about 700 GFLOP/s from a single thread, with CPU time equal to wall time. One core's NEON units cannot exceed about 110. So Accelerate is using hardware other than the ordinary SIMD units (Apple's matrix coprocessor), and the thread-count setting does not govern it.

No code built from NEON intrinsics can match that, which is why the project's stated peer is ONNX Runtime, whose CPU kernels use the same instructions this compiler emits.

10.1 Two questions, kept apart

Every loop transformation raises two separate questions.

Legality: does the transformed loop compute the same values? This has a definite answer, and the compiler must be able to prove it. A rewrite that cannot prove it refuses (throws ScheduleError) and changes nothing.

Profitability: is it faster? This depends on the machine and the sizes, and is answered by measurement. The rewrites never ask it. The caller, either the default schedule or the autotuner, decides what to apply.

A schedule is a choice of which rewrites to apply, to which loops, with which parameters. The program's meaning is fixed by the naive loop nest; the schedule only changes how it runs. This separation, introduced by the Halide system, is what makes an autotuner possible: it can try any schedule without any risk to correctness.

10.2 Dependence analysis

Legality comes down to one question about a loop: are its iterations independent? That is, does any iteration read or write an element that a different iteration writes? If not, the iterations can run in any order, interleaved, or simultaneously.

Recall that the loop IR has no scalar variables (section 7.1). Every effect of an iteration is a Store to a buffer and every input is a Load. So the question is entirely about array indices.

Index expressions are affine

Every index the lowering produces is a sum of loop variables times constants plus a constant, for example i3 * 20 + i7 * 5 + 2. Such an expression is called affine. affine() converts an expression into that form: a map from variable to coefficient, and a constant. Anything else (an index that is itself loaded from memory, as in Gather) is "not affine" and is treated conservatively.

Each loop variable has a known range, 0 to extent - 1, so the smallest and largest value of an affine expression can be computed.

The proof the analysis looks for

For a loop over v, and for every buffer the loop body writes, the analysis looks for one axis along which every access to that buffer in the body (loads and stores alike) has an index of the form

c * v  +  r  +  (terms in outer loop variables)

where

  • c >= 1 is the same constant in all of them,
  • the outer-variable part is identical in all of them,
  • r (inner loop variables and constants) varies over a range narrower than c.

If such an axis exists, each iteration of v touches its own slice of the buffer along that axis, slices of different iterations cannot overlap, and the iterations are independent. If two iterations v1 != v2 collided, their r values would have to differ by a multiple of c, which a spread smaller than c rules out.

Anything the analysis cannot prove counts as dependent. It is sound (it never says "independent" wrongly) but not complete (it sometimes says "dependent" when a cleverer analysis could prove otherwise).

Examples

The naive matrix product:

for i: for j: { C[i,j] = 0
                for p: C[i,j] = C[i,j] + A[i,p] * Bt[j,p] }
  • Loop i: C is the only buffer written. Along axis 0 every access is at i. Independent.
  • Loop j: along axis 1 every access is at j. Independent.
  • Loop p: no index of C contains p at all. Every iteration writes the same element. Dependent. (It is a sum, a special case handled by vectorize below.)

Cumulative sum, out[j+1] = out[j] + in[j+1]: along the axis, one access is at j + 1 and another at j. The spread of r is 1, not less than c = 1. Dependent, correctly: each step needs the previous one.

After blocking, an index looks like jc * 20 + jj with jj in 0..19. For the loop over jc: c = 20, r = jj with spread 19, which is less than 20. Independent. This is why the proof is phrased with a stride and a range rather than "the index is exactly v".

Buffers that share memory

The analysis treats two buffers as the same when they are the same bytes under the same shape (an in-place kernel's input and output). If two buffers overlap under different shapes, the indices cannot be lined up, and the loop is declared dependent.

10.3 The rewrites

Each takes a kernel body and the variable of the loop to act on, and returns a new body. Loops are named by their variable. Some rewrites copy a nest (a main part and a leftover part), which leaves several loops binding the same variable in sibling positions; a variable then names all of them and the next rewrite applies to each.

split(v, factor)

for v in 0..N: S(v)
        becomes
for outer in 0..N/f:  for inner in 0..f:  S(outer*f + inner)
for tail  in 0..N%f:                      S((N/f)*f + tail)

Iterations run in exactly the same order, so it is always legal and on its own changes nothing. It exists to create the loops that interchange moves.

interchange(v)

for v: for w: S     becomes     for w: for v: S

Requires v's body to be exactly one loop, and v's iterations to be independent. Why independence is the condition: afterwards, iteration (v, w) can run before (v', w') with v' < v. That reorders things across different values of v, which is harmless exactly when different values of v never depend on one another.

unroll_and_jam(v, factor)

Unrolling a loop by 4 means writing the body four times per step (for v, v+1, v+2, v+3) and stepping by 4. Jamming means fusing those four copies all the way down: rather than four copies of the inner loops one after another, there is one copy of the inner loops whose innermost statements are each repeated four times.

for i: for p: C[i] += A[i,p] * b[p]
        becomes (factor 2)
for io: for p: { C[2*io]   += A[2*io,  p] * b[p]
                 C[2*io+1] += A[2*io+1,p] * b[p] }

The effect: one pass over p now computes two elements of C. They share the load of b[p], and each has its own running sum, an independent dependency chain (section 9.3).

Requires v's iterations to be independent (the copies' statements now run interleaved; each copy still sees its own statements in order). Leftover iterations, when N is not a multiple of the factor, are jammed too, all at once, into a smaller group. Left as a one-at-a-time loop they would have too few accumulators; this was measured to matter (a 64-column product with a 5-wide group left 4 columns, 6% of the work, running at a third of the speed).

vectorize(v, interleave)

Marks a loop to run in SIMD lanes. It is legal when the body is a list of stores and each store is one of two kinds:

  • Elementwise: iteration v writes element v of a contiguous run (the index along the last axis is v plus something constant in this loop). Anything else in the body that touches the same buffer must touch exactly the same element, or a different row entirely. Four iterations then become one vector store.
  • Reduction: every iteration combines into the same element, as t = t + e or t = max(t, e), and nothing else in the loop touches that element. The vector loop keeps the running value in a register and reorders the additions, which is the one place the compiler changes floating-point order (section 9.7).

The values involved must be something a vector can hold: 32-bit float arithmetic on things that are either the same for the whole loop (broadcast into all lanes) or read from consecutive addresses. That rules out Select, integer and boolean values, pow, and reads that stride across rows (as in Permute).

plan_vector_loop makes this decision and reports, for each store, which kind it is. The code generator calls the same function, so the two cannot disagree.

interleave is the number of independent accumulator sets for a reduction. A lone sum (layer norm's mean) gets 4, so that four dependency chains run at once. A loop that already has many accumulators gets 1.

parallelize(v)

Marks a loop to run on several threads. Requires independence.

10.4 Deriving the fast matrix product

This is the central piece of the project. Start from the naive nest, with A of shape [m, k] and Bt of shape [n, k] (section 7.3):

for i in 0..m:
  for j in 0..n:
    C[i,j] = init
    for p in 0..k:
      C[i,j] = C[i,j] + A[i,p] * Bt[j,p]

Each element of C is a dot product of a row of A and a row of Bt. Both rows are contiguous in memory. That is why the layout pass (section 6.9) put the product in this form.

As written it has two problems. There is one accumulator, so it runs at a fraction of the FMA units' capacity (section 9.3). And it is not vectorized.

Step 1: register tiling

Apply unroll_and_jam to i with factor 4 and to j with factor 5. The innermost loop becomes:

for p in 0..k:
  C[i+0,j+0] += A[i+0,p] * Bt[j+0,p]
  C[i+0,j+1] += A[i+0,p] * Bt[j+1,p]
  ...                                      20 statements: a 4 x 5 tile of C
  C[i+3,j+4] += A[i+3,p] * Bt[j+4,p]

One pass over p now computes twenty elements of C. It reads 4 rows of A and 5 rows of Bt: 9 loads feeding 20 multiply-adds, because each loaded value is used several times.

Step 2: vectorize p

Each of the twenty statements is a reduction over p. Vectorizing keeps each in its own NEON register and processes four values of p per step:

  • 20 accumulator registers,
  • 4 registers for the loaded A values, 5 for Bt,
  • 29 of the 32 registers in use.

Every step does 9 vector loads and 20 FMAs, and there are 20 independent dependency chains, enough to keep all four FMA units busy on every cycle. This loop is what high-performance libraries call the micro-kernel. Here it was not written by hand: it fell out of two general rewrites.

The tile shape is a trade-off inside a fixed budget: rows * cols + rows + cols <= 32 registers. 4x5 has 20 accumulators. 4x6 would need 34 registers and spill to memory, which measured at half speed.

Step 3: cache tiling

The register tile fixes the innermost loop. The loops around it decide what is in cache.

Whichever operand has more rows is put on the outside (if that is Bt, an interchange swaps i and j). Call it the big operand. It is then split into blocks of rows, and the block's inner loop is interchanged inside the loop over the other operand:

for block of the big operand's rows:        the block is loaded into L1 once
  for each tile of the small operand:
    for each tile of rows in the block:
      (the micro-kernel)

Every row of the small operand meets a block that is already in L1. The big operand is streamed through memory exactly once.

The block size is chosen so that the block, plus what it is multiplied against, fits comfortably in the 128 KB L1 cache (the default aims for about 64 to 72 KB in total).

Step 4: threads

The outermost loop is marked parallel. Each thread gets a contiguous range of blocks, and therefore its own rows or columns of C.

The result

    for i6 in 0..4:                         tiles of 4 rows of A

What this design is, and is not

The standard design for a fast matrix product (GotoBLAS, BLIS) is different: it packs both operands, copying them into contiguous buffers arranged for the micro-kernel, and its micro-kernel is in "outer product" form (each step multiplies a short column of A by a short row of B).

This project uses the "dot product" form on unpacked operands instead. The reasoning:

  • At T=16 the operand A has only 16 rows. Packing a weight matrix costs as much as multiplying by it.
  • Packing the weights once at load time is possible, but costs the same memory as transposing them at load time, which is what dot form needs.
  • The largest operand of all, the 154 MB embedding table, is already in the layout dot form wants.

The cost, measured: the outer-product micro-kernel peaks about 5% higher than the dot-product one, and at T=1024 on AC power ONNX Runtime's kernel (which is of that kind) is about 9% faster than ours on large products. Section 12.6 has the numbers.

10.5 The default schedule

schedule_program applies, to every kernel:

  1. If it is a dot-form matrix product: the steps of section 10.4, with parameters from default_matmul_params (or from the autotuner's cache). The tile is 4x5, swapped to 5x4 or 4x4 if that leaves clearly fewer leftover rows.
  2. vectorize every innermost loop that plan_vector_loop accepts.
  3. parallelize each outermost loop if its iterations are independent and the kernel is big enough to repay waking threads. "Big enough" is an estimate of the work (stores executed, with a store that calls exp or tanh counted as twenty) compared against a threshold. Because shapes are static, this decision is made at compile time, per kernel.

What ends up vectorized in GPT-2: all matrix products, layer norm (three loops), softmax (three loops plus the zero fill), GELU, the additions and scalings, and the embedding lookup (a contiguous copy). What stays scalar: permutes (strided reads) and slices' outer structure. They are under 1% of the run.

10.6 Vector loops in generated C++

For a loop over v with 4 lanes and interleave U, the emitter writes:

accumulators = identity                         one per reduction and per interleave slot (0 for a sum, -inf for a max)
for (v = 0; v + 4*U <= N; v += 4*U)  body, U vectors at a time
for (;      v + 4   <= N; v += 4)    body, one vector            (only if U > 1)
scalars = target (+) lanes of accumulators      fold each reduction into one float
for (;      v < N; ++v)              scalar body                  (the leftover iterations)
target = scalars

The mean of a layer norm, as generated:

float32x4_t acc0_0 = vdupq_n_f32(0.0f);       // four independent accumulators
float32x4_t acc0_1 = vdupq_n_f32(0.0f);
float32x4_t acc0_2 = vdupq_n_f32(0.0f);
float32x4_t acc0_3 = vdupq_n_f32(0.0f);
int64_t i1 = 0;
for (; i1 + 16 <= 768; i1 += 16) {
  const float32x4_t x0 = vld1q_f32(v6 + ((i0 * 768) + i1));
  acc0_0 = vaddq_f32(acc0_0, x0);
  const float32x4_t x1 = vld1q_f32(v6 + ((i0 * 768) + (i1 + 4)));
  acc0_1 = vaddq_f32(acc0_1, x1);
  ...
}
float r0 = t9_mean[i0] + vaddvq_f32(vaddq_f32(vaddq_f32(vaddq_f32(acc0_0, acc0_1), acc0_2), acc0_3));
t9_mean[i0] = r0;

Details of the emitter:

  • Loop-invariant values (a scalar constant, the row's mean) are broadcast into a vector once, before the loop.
  • Each distinct memory operand is loaded once per iteration, however many statements use it. In the matrix product, each of the 9 rows is loaded once and used in 4 or 5 FMAs.
  • A value just stored is reused from its register if a later statement reads it (softmax writes exp(...) and immediately adds it to the sum).
  • a + b * c is emitted as one FMA.
  • Leftover loops are omitted when the trip count is a known multiple of the vector width.

The instruction-set table

src/codegen/isa.h is the only place that names an intrinsic: a struct with one string per operation (add = "vaddq_f32", fma = "vfmaq_f32", ...). The emitter asks the table. Supporting another instruction set (AVX2 on x86) means adding a second table and a second math header; the loop IR and emitter stay as they are.

10.7 Vector exp and tanh (runtime/mlc_neon.h)

The C library computes exp and tanh one float at a time. A vectorized loop that had to call it once per lane would gain nothing. So there are two handwritten vector functions.

exp. Write x = n * ln(2) + r with n an integer and |r| <= 0.35. Then exp(x) = 2^n * exp(r).

  • n = round(x / ln 2).
  • r = x - n * ln 2, computed with ln 2 split into two parts so the first subtraction is exact.
  • exp(r) is approximated by a degree-6 polynomial, accurate to float precision on that short interval. The coefficients are from the Cephes math library.
  • 2^n is built directly by writing n + 127 into the exponent bits of a float.

The input is first clamped to [-87.3, 88.0] so the result is never zero, subnormal, or infinite. Measured relative error over the whole range: below 2.5e-7.

tanh. tanh(x) = 1 - 2 / (exp(2x) + 1), with x clamped to [-10, 10], beyond which tanh is 1 or -1 to float precision. Absolute error below 2.5e-7. Relative error is poor for |x| below about 0.001, where the subtraction cancels; GELU multiplies by x again, so it does not matter here. A general-purpose tanh would switch to a polynomial near zero.

Both are tested against the C library over a fine grid of inputs (tests/test_schedule.cpp).

10.9 The thread pool (runtime/mlc_runtime.cpp)

mlc_parallel_for(n, fn, context) runs fn(context, begin, end) over 0..n, cut into one contiguous range per thread, and returns when all are done.

  • A fixed pool. threads - 1 worker threads are created once and live as long as the model is open. The calling thread takes a range itself.
  • Static scheduling. The range is cut into as many pieces as there are threads, decided up front. Nothing is handed out on demand, which costs nothing per iteration and keeps each thread on its own stretch of memory.
  • Spin, then sleep. An idle worker watches for the next job in a tight loop for a short while (tens of microseconds) and only then goes to sleep on a condition variable. Kernels at small T last tens of microseconds and follow one another closely; workers that slept between them would spend longer waking than working.
  • A job lives on the caller's stack. It is published through an atomic pointer. Before returning, the caller un-publishes it and waits for every worker that might still hold the pointer to let go, tracked with a counter that workers increment before reading the pointer.
  • No nesting. A parallel loop reached from inside a parallel range runs on the calling thread.
  • Quality of service. Workers request the class that makes macOS place them on performance cores.
  • Thread count. mlc_set_threads(n), or the MLC_THREADS environment variable, or by default the number of performance cores.

11. The autotuner

Chapter 10 ended with a default schedule whose parameters (a 4x5 tile, a block of about 64 KB) were chosen by hand from a few measurements. The autotuner (src/tune/, mlc tune) replaces hand-picking with a search: try many schedules, time each, keep the best, and write the answers to a file so that later compiles need no measuring.

It works, it is tested, and on this model it found very little. Both halves of that sentence are worth understanding.

11.1 Why tune by measurement

Which tile shape or block size is fastest depends on details that are hard to predict from first principles: how many registers the C++ compiler really manages to use, how the prefetcher reacts to a particular access pattern, how the caches are shared. Timing a candidate takes a fraction of a second and is always right about the machine it ran on. So production systems (ATLAS for linear algebra, FFTW for Fourier transforms, TVM for neural networks) search.

The separation of chapter 10 is what makes it safe. A schedule cannot change what is computed, so any point the search tries is a correct program.

11.2 What is tuned

The schedule of each distinct matrix product, as a small struct:

struct MatmulParams {
  int tile_rows = 4, tile_cols = 5;  // the register tile
  bool cols_outside = false;         // which operand is blocked and streamed once
  int64_t block_rows = 0;            // rows per cache block; 0 = no cache tiling
};

Applying any value of this struct is the same sequence of rewrites as section 10.4 (apply_matmul). The hand-picked default is just one value, computed by default_matmul_params.

Optionally one global parameter: the work threshold below which a kernel stays on one thread (--tune-threshold).

Nothing else is tuned. Every other choice in the schedule is either forced by legality or made no measurable difference when tried by hand.

11.3 Kernel signatures

GPT-2 has 73 matrix products but only 7 distinct ones at a given T: the same shapes repeat in all twelve layers. Each dot-form kernel carries a signature, the operator and operand shapes:

gemm [16,768] x [2304,768]^T
matmul [12,16,64] x [12,16,64]^T
matmul [16,768] x [50257,768]^T

Two kernels with the same signature are the same loops over different memory, so a schedule measured for one is valid for all. The tuner works per signature.

11.4 The search space (Space)

A candidate is a point with three coordinates:

  • tile: an index into the list of all tiles (r, c) with r * c + r + c <= 32 (they fit the registers), r * c >= 12 (enough accumulators to matter), and r, c no larger than the matrix. About 21 tiles for a large product.
  • block: an index into a list of block sizes expressed as fractions of the L1 cache (1/16, 1/8, 3/16, 1/4, 3/8, 1/2, 3/4, 1, 2, 4), or -1 for "no cache tiling". The L1 size is read from the operating system (sysctl hw.perflevel0.l1dcachesize), so the same fractions mean the right thing on another machine. A block is rounded to a whole number of tiles.
  • which operand is outside: two choices.

That is 21 * 11 * 2 = 462 points for a large product.

The coordinates are arranged so that neighbouring values are similar schedules, which is what makes "change one coordinate a little" a meaningful move.

A test (tune_every_point_of_the_space_is_a_correct_schedule) applies every distinct point of a small product's space, over a hundred schedules, and requires bit-identical results from the loop interpreter. The tuner may pick any point, so every point has to be right.

11.5 Measuring a candidate

Timing a schedule requires generating code for it and running it. Doing that one candidate at a time would mean one C++ compiler run each. Instead:

  1. Build a small graph containing the same product several times (up to eight), all reading the same two operands.
  2. Lower it. The results are never read, so the memory planner gives every copy the same piece of the arena. The copies differ in schedule and in nothing else.
  3. Schedule each copy with a different candidate.
  4. Generate C++, build one shared library, load it.
  5. Run it repeatedly with the runtime's per-kernel timer. In each pass all candidates run in turn.
  6. For each candidate keep the minimum time over all passes.

Two points of method:

  • Interleaving. Because every candidate runs within each pass, anything that changes the machine's speed over time (heat, another process) affects all of them about equally.
  • Minimum, not mean. On a quiet machine, noise only ever adds time: an interruption, a cache miss caused by something else. The smallest sample is the best estimate of what the code can do.

11.6 The search

For one product, with the default settings:

  1. Generation 0: the default schedule plus 16 random points.
  2. Two more generations: take the three best so far and mutate them. A mutation changes one coordinate by a small step: a nearby tile, the next block size up or down, or the other operand outside. Eight new candidates per generation. This is a simple evolutionary search.
  3. The final: the three best candidates and the default, measured again side by side for three times as long.
  4. The decision: a candidate replaces the default only if it wins the final by more than 2%.

So 33 of 462 points are tried per product.

Step 3 exists because of a statistical trap. If you measure 33 schedules that are all really the same speed, with a little noise each, the best-looking one will appear 1 to 2% faster than the default by luck alone. Picking it would be fitting noise. Re-measuring the leaders against the default, for longer, and demanding a margin, guards against that. An early version with a 1% margin produced "improvements" that a second run did not reproduce.

11.8 Validation on the whole model

After tuning the products for a thread count, mlc tune builds the whole model twice, once with default schedules and once with tuned ones, and times them in alternating runs (default, tuned, default, tuned, ...), again so that drift affects both alike.

11.9 What it found

54 entries (7 products, 4 sequence lengths, 2 thread counts, minus two duplicates). The default was replaced in 12.

Whole model, default against tuned, from the tuner's own alternating runs (median seconds):

T=16 T=64 T=256 T=1024
1 thread, default 0.0473 0.1806 0.7038 3.1761
1 thread, tuned 0.0466 0.1814 0.6998 3.1672
4 threads, default 0.0228 0.0628 0.2274 0.9868
4 threads, tuned 0.0222 0.0634 0.2300 0.9518

Tuned is ahead by 1.5 to 3.7% in three cells and within about 1% either way in the rest, which is noise. In the final benchmark session the two builds trade places from cell to cell.

Why so little. On one core, every sensible schedule runs the large products at 97 to 101 GFLOP/s. The kernel is limited by how fast the FMA units can go (section 9.3), not by the cache. A search over cache-related parameters has nothing to find. The products that did improve are the memory-bound ones on four threads: the 3072-wide projection at T=1024 went from 287 to 332 GFLOP/s, and the T=16 output projection from 296 to 348.

Random search was enough. In most products the best point after two generations of mutation was the best random point.

The tuner optimizes the wrong thing at small T. It times a kernel whose weight matrix stays in cache between runs. In the real model at T=16, every call reads each weight once from main memory (section 12.6). A schedule that is best with a warm operand is not necessarily best with a cold one. Making the measurement cold is listed as future work.

So the milestone's exit criterion, "tuned schedules beat hand-picked defaults on the model", is met only weakly. The honest conclusion is that the defaults from M4 were already at this machine's limit for this model, and the tuner mostly confirmed them.

11.10 A bug worth remembering

The first version rebuilt candidate libraries at the same file path. Results were nonsense: a "winner" 13% slower than the search's best. On macOS a library with thread-local state is never really unloaded, so loading the same path again returned the old code, and the tuner was timing stale candidates under new labels. Every candidate library now gets a fresh path and is deleted after use.

The general lesson: a measurement harness needs to be tested as carefully as the thing it measures.

12. Testing, benchmarking, and the results

Two questions remain about any compiler: is its output right, and how fast is it? This chapter covers how each was answered, and then goes through the final numbers.

12.1 The kinds of test

Unit tests (tests/*.cpp, 103 of them, run by the mlc_tests program). The test "framework" is one header, tests/check.h, about 70 lines:

  • TEST(name) { ... } defines a function and a static object whose constructor adds the function to a global list before main runs.
  • CHECK(cond) records a failure and keeps going, so one run reports every problem.
  • CHECK_NEAR(a, b, tol) and CHECK_THROWS(expr, ExceptionType) do what they say.
  • mlc_tests gelu runs only the tests whose name contains gelu.

Differential tests. Most unit tests do not compare against hand-computed answers. They compute the same thing two ways and compare. tests/helpers.h has the building blocks:

  • lowering_matches(graph, outputs): run the graph interpreter; lower the graph and run the loop interpreter; compare every output. Done twice, with staging off and on.
  • same_after(...) in the schedule tests: apply a loop rewrite and require the loop interpreter to give bit-identical results. This is possible because the loop interpreter runs every loop serially in order, and none of the rewrites changes the order in which any one element's terms are added.
  • tiny_transformer(g, ids): one attention block and one MLP block at toy size (5 tokens, width 8, 2 heads), built from the same operators in the same arrangement as the real export, including the nine-node GELU and the mask guard. It goes through every stage: graph interpreter, optimized graph, loop interpreter, compiled code.

Negative tests. Things that must be rejected: a GELU lookalike with a wrong constant must not be fused; a loop with a carried dependence must not be vectorized or parallelized; a program that stores to read-only memory must fail verification; an out-of-range gather index must be caught. An optimizer that fires when it should not is worse than one that never fires.

Every-point tests. The autotuner can pick any schedule in its space, so one test applies every distinct point of a small product's space and checks each.

Compiled-kernel tests at awkward sizes. compiled_kernels_match_the_graph_interpreter_at_awkward_sizes builds real shared libraries for matrix products with 7 rows against tiles of 2, 11 columns against tiles of 3, and 13- and 9-element rows against 4 SIMD lanes, so that every leftover path in the generated code is exercised. It also checks that one thread and three threads give identical bits.

End-to-end tests (ctest, defined in CMakeLists.txt). For each T, on the real model against PyTorch's golden logits:

Test Checks
golden_T* graph interpreter on the imported graph
optimized_T* graph interpreter on the optimized graph
compile_T*, compiled_T* the full pipeline to a shared library, run with the default thread count
compiled_T16_one_thread the same library on one thread
compile_tuned_T16, compiled_tuned_T16 built from the autotuner's cache
compile_unoptimized_T16, compiled_unoptimized_T16 every optimization off (the baseline for ablations)

T=256 and T=1024 are labelled slow; ctest -LE slow skips them.

Sanitizers. A second build configuration (build/asan, -DMLC_SANITIZE=ON) compiles everything with AddressSanitizer and UndefinedBehaviorSanitizer, which instrument the code to detect out-of-bounds accesses, use after free, and undefined arithmetic at run time. In that configuration the generated code is built with the sanitizers too, so a kernel that reads one element past a buffer is caught.

Self-checks inside the compiler. These run on every compile, not only in tests: the graph verifier after import and after every pass; the importer's comparison of every inferred type with PyTorch's; the loop verifier after lowering and after scheduling; legality checks in every rewrite.

12.2 The correctness criterion

From STEERING.md section 6, implemented in compare_logits (src/main.cpp): on the golden input, the maximum absolute difference in any logit is at most 1e-3, no logit is NaN or infinite, and the largest logit is at the same index at every position.

Observed across all builds: 1.3e-4 to 4.9e-4. ONNX Runtime's own difference from PyTorch is also 4.9e-4 at T=256.

12.3 How the benchmarks work

bench/run.py times whole forward passes. Rules (STEERING.md section 7):

  • Same model, same input. Every system imports export/model.py.
  • A fresh process per (system, thread count). Libraries size their thread pools at startup, and torch.compile bakes the thread count into generated code. bench/worker.py is that process.
  • Warm-up excluded. Five untimed runs first. The first calls pay for one-time work: memory being faulted in, thread pools starting, torch.compile and ONNX Runtime doing their own compilation.
  • At least 30 timed runs, and at least 2 seconds of measuring. Median and minimum are reported; raw samples go to a JSON file.
  • Thread counts set explicitly and equally: 1 and 4.
  • Every system's output is checked against the golden logits in the same run.
  • The environment is recorded: library versions, which BLAS PyTorch uses, power state.

The four systems:

System What it is
PyTorch eager the model run normally, under torch.inference_mode()
torch.compile PyTorch's JIT compiler, with dynamic shapes disabled so it specializes per T as this project does
ONNX Runtime the model exported to ONNX and run by Microsoft's inference engine, all graph optimizations on
mlc this project, loaded through ctypes; mlc-tuned uses the autotuner's cache

Supporting scripts:

Script Produces
bench/gemm.py each distinct matrix product timed alone, in mlc, ONNX Runtime, and PyTorch
bench/per_op.py time per kind of operation, from mlc exec --profile
bench/ablate.py the model rebuilt with optimizations switched on one at a time (cumulative) or off one at a time (leave-one-out)

An ablation answers "what is this optimization worth?" by building the same thing with and without it. Cumulative ablations show what each adds on top of the previous ones; leave-one-out shows what is lost without each. They can disagree when optimizations interact, which is why both exist.

12.4 Reading performance numbers honestly

Lessons this project paid for:

  • Compare only within one session. The laptop's power state changed results by a factor of two (section 9.9).
  • Minimum for "what can the code do", median for "what will you see". They diverge when something throttles.
  • A standalone kernel benchmark flatters. It reuses warm data (section 12.6).
  • Differences under about 2% between sessions are noise on this machine.
  • A result measured on a throttled machine can reverse at full speed.

12.6 Explaining the numbers

Where the time goes (bench/results/per_op.md, one thread):

Matrix products are 96 to 98% of every run. Everything about the comparison is about them.

The matrix products alone (bench/results/gemm_T*.md, GFLOP/s, weighted by the model's use):

T=16, 1 thr T=16, 4 thr T=1024, 1 thr T=1024, 4 thr
mlc 90.1 268.6 94.8 342.5
ONNX Runtime 71.6 237.9 103.1 376.1
PyTorch (Accelerate) 378.7 395.8 925.6 941.9
  • At T=1024, ONNX Runtime's kernel is about 9% faster than ours on large products. This is the cost of the dot-product design without packing (section 10.4). In the whole model we are level anyway, so ONNX Runtime loses elsewhere what it gains here.
  • At T=16, our kernel is the faster one alone, yet the whole model is slower. The standalone benchmark multiplies by the same weight matrix over and over, so the matrix stays in cache. In the model, each call reads all 494 MB of weights from main memory exactly once, and at T=16 uses each value only 16 times. The run is limited by memory bandwidth (section 9.4), not arithmetic. In the model our dense layers reach about 82 GFLOP/s on one thread and about 260 on four, against 100 and 370 alone.
  • What ONNX Runtime does better in that situation was not found. Software prefetch (asking the CPU to fetch upcoming data early) was tried in a hand-written copy of the kernel over 48 cold matrices and made it 13 to 30% slower.

Graph passes (m3_ablation_*.md): no measurable effect on time (0.634 s to 0.637 s at T=16; 38.4 s to 37.7 s at T=1024). They are 3% of the story at most because they cannot touch matrix products. Their effect is on memory and size (section 6.11).

13.2 What is unfinished or unexplained

Collected from docs/log.md and docs/writeup.md.

Open performance problems

  1. Small T on four threads. 57% behind ONNX Runtime at T=16. The dense layers are limited by reading cold weights from memory. What ONNX Runtime does better was not found.
  2. Large products are 9% behind ONNX Runtime's kernel. A packed outer-product kernel would likely recover it for large shapes.
  3. The autotuner measures warm operands, which is not the situation in the model at small T.
  4. The small-inner-dimension product (q @ k^T, inner size 64) runs at about 85% of the others' rate because per-tile overhead is a larger share.

Open costs

  1. 340 MB of persistent memory for transposed weights. Storing the weights transposed in the weights file would remove it.
  2. Permutes and slices are real copies. They could be views (strided buffers), which the loop IR does not have.

Never explained

  1. noalias on its own changes nothing, though aliasing was identified in M2 as what stopped clang's vectorizer.

Not built

  1. Rewrites fuse, standalone unroll, general reorder: nothing needed them.
  2. A second instruction set (AVX2).
  3. M7: the Triton GPU backend. Needs a Linux machine with an NVIDIA GPU.
  4. Stretch: KV-cached decoding. Generating one token at a time while reusing earlier attention keys and values. Needs a second export and state carried between calls.

13.4 Glossary

Ablation. Measuring what one optimization contributes by building with and without it.

Accumulator. A variable (in generated code, a register) holding a running sum or maximum.

Affine expression. A sum of variables times constants, plus a constant. All array indices in the loop IR are affine.

Aliasing. Two names referring to the same memory.

AOT (ahead-of-time) compilation. Compiling before the program runs, to a file.

Arena. One block of scratch memory holding every intermediate tensor at a compiler-chosen offset.

ATen. PyTorch's C++ tensor library; its operators are what torch.export records.

Attribute. A non-tensor parameter of a graph node (an axis, a shape).

Best fit. Allocation policy: use the smallest free block that is large enough.

Binding time. When a value becomes known: compile time, load time, or run time.

BLAS. The standard interface for linear algebra routines; Accelerate, OpenBLAS, and BLIS implement it.

Blocking / tiling. Splitting a loop so that work is done on cache-sized pieces.

Broadcasting. Treating a size-1 axis as repeated to match another tensor.

Cache. Small fast memory holding recently used data. L1 is the smallest and fastest.

Cache line. The 64-byte unit caches work in.

Causal mask. The rule that position i may attend only to positions 0..i.

Coalescing. Merging adjacent free memory blocks.

CSE (common subexpression elimination). Merging nodes that compute the same value.

DCE (dead code elimination). Removing nodes no output depends on.

Dependence. One loop iteration reading or writing what another writes.

Dependency chain. Instructions each needing the previous one's result.

Differential test. A test that compares two implementations of the same function.

Dot product. sum of a[p] * b[p].

dtype. The element type of a tensor: f32, i64, or bool.

Elementwise. An operation applied independently to each element.

Extent. A loop's trip count.

Flop. One floating-point operation. GFLOP/s: billions per second.

FMA. Fused multiply-add: a + b*c as one instruction.

Folding (constant folding). Evaluating at compile time what does not depend on input.

Fusion. Replacing several operations by one that does the same work in one pass.

Gather. Looking up rows of a table by index.

GEMM. General matrix multiply. In this project Gemm is a @ b + bias.

Golden output. PyTorch's saved result on a fixed input; the reference answer.

Graph IR. The compiler's representation of the model as operations on whole tensors.

Hoisting. Moving a computation to where it runs less often.

Init kernel. A kernel run once at load time.

Interchange. Swapping two nested loops.

Interleave. The number of independent accumulator sets in a vectorized reduction.

Intrinsic. A C++ function that compiles to one specific instruction.

IR (intermediate representation). A compiler's internal form of a program.

JIT (just-in-time) compilation. Compiling during execution.

Kernel. The loop nest for one graph node; one function in generated code.

Lane. One of the four float slots in a NEON register.

Latency. Cycles from an instruction's inputs being ready to its result.

Liveness. A value is live from its definition to its last use.

Logits. The model's output scores, one per vocabulary token per position.

Loop-carried dependence. An iteration depending on an earlier iteration of the same loop.

Lowering. Translating to a more concrete representation.

Memory planning. Deciding at compile time where each tensor lives.

Micro-kernel. The innermost loop of a matrix product, operating on a register-sized tile.

mmap. Mapping a file into memory so its bytes appear at addresses, loaded on first touch.

NEON. The SIMD instruction set of arm64 CPUs.

Oracle. Whatever supplies the right answer in a test.

Outlining. Moving a loop body into its own function (for threads).

Packing. Copying a matrix into a contiguous buffer arranged for a micro-kernel. Not used here.

Pass. A function from a program to an equivalent, better program.

Persistent memory. Memory filled by init kernels at load and read on every call.

Prefetcher. CPU logic that fetches memory ahead of a detected access pattern.

Pure. Having no side effects; the result depends only on the inputs.

Rank. The number of axes of a tensor.

Reduction. Combining many values into one (a sum, a maximum).

Register tiling. Unroll-and-jam of two loops so a tile of results is computed at once in registers.

Residual connection. x + f(x).

Row-major. Memory layout in which the last axis varies fastest.

Schedule. The choice of loop transformations and their parameters.

Signature. A kernel's operator and operand shapes; kernels with the same signature share a tuned schedule.

SIMD. Single instruction, multiple data.

Softmax. exp(x_j) / sum of exp(x_i): turns scores into probabilities.

Sound (analysis). Never claims a property that does not hold.

SSA (static single assignment). Every value is defined exactly once.

Staging. Sorting computations by binding time.

Stride. How far in memory one step along an axis moves.

Tensor. An array of numbers with a shape and a dtype.

Throughput. How many of an instruction can start per cycle.

Tracing. Recording the operations a program performs on an example input.

Unroll-and-jam. Unrolling an outer loop and fusing the copies into the inner loop.

Value numbering. Giving each distinct computation a number so duplicates can be found; how CSE is implemented.

Vectorize. Rewrite a loop to use SIMD instructions.

Weight tying. Using the same parameter tensor for the input embedding and the output projection.
